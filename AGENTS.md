# Проект BeeRouting (Хакатон Лидеры цифровой трансформации)

# 1. Стек технологий
* **Back** - Python 3.10+ + numpy, ООП, Django + Django Rest Framework, PostgreSQL + PostGIS, Google OR-Tools
+ вау-альтернативный инструмент: метаэвристическая оптимизация, основанная на DE - ICO
используй numba JIT для ускорения математики (если функция уже не ускорена и не на C/C++)
Не использовать Numba для Django ORM, API-кода, OR-Tools и других участков, где JIT не дает практического выигрыша.

* Бизнес-логика оптимизации не должна находиться во views или serializers.
* OR-Tools является базовым надежным решателем системы.
* Поддержать отдельный интерфейс solver'а. Это должно позволять иметь несколько реализаций:
ORToolsOptimizer
ICOOptimizer
HybridOptimizer

* ICO
В проекте допускается и приветствуется использование кастомной метаэвристической оптимизации ICO:
https://github.com/Krash13/IcoCEC/blob/island_DE/cec2017/countries_algorithm_v2.hpp

ICO является экспериментальным/исследовательским solver'ом и потенциальным конкурентным преимуществом проекта.

Не заменять рабочий OR-Tools solver на ICO, пока ICO не проходит одинаковые тестовые сценарии.

Предпочтительные варианты применения ICO:

    - отдельный solver для сравнения с OR-Tools;
    - improvement phase после получения начального решения;
    - оптимизация части решения;
    - гибридный OR-Tools + ICO pipeline.

---

* Hard constraints и soft constraints

Обязательно разделять жесткие ограничения и оптимизационные штрафы.

* Hard constraints

Назначение считается невозможным, если нарушено жесткое ограничение.

Примеры:

  - отсутствие необходимой квалификации;
  - отсутствие обязательного оборудования;
  - отсутствие необходимого транспорта;
  - недоступность инженера;
  - невозможность выполнения заявки в рамках обязательных временных ограничений.

---

* Soft constraints

Soft constraints — мягкие ограничения. Их нарушение допускается, но увеличивает стоимость решения.

Примеры:

нарушение SLA;
опоздание;
увеличение времени в пути;
сверхурочная работа;
неравномерная загрузка инженеров;
изменение уже сформированного плана при перепланировании.


* **Фронт** - Vue.js, Vite, TS, Vuetify, также MapLibre GL JS — при необходимости для визуализации карты и маршрутов.
* **Rounting service** - OSRM
* **LLM** - возможные варианты API-ключ `GigaChat API`/`YandexGPT API` или local vllm (с моделью Qwen3.8-27B в non-thinking)
* **Инфраструктура** - Docker, Docker Compose. Для длительных задач (оптимизация Google OR-Tools, ICO, LLM, построение больших матриц маршрутов) - в будущем разрешено добавить асинхронность `Celery` + `RabbitMQ`.
* **Объяснимый ИИ (Explainable AI / XAI):** Основная задача ИИ-агента — парсинг текстовых или структурированных логов оптимизатора и генерация пошагового обоснования причин выбора маршрута на понятном человеку русском языке. Промпты должны быть четкими и конкретными.
Решение о назначении инженера и построении маршрута принимает Optimization Engine, а не LLM.
Optimization Engine должен по возможности формировать структурированные данные о причинах принятого решения: соответствие квалификации, наличие оборудования, ETA, временное окно, SLA, дополнительное время движения, причины отклонения альтернативных исполнителей и т. п.
LLM не должна придумывать причины, которых нет в данных Optimization Engine.

# 2. Принципы кодинга
* **Понятность и хорошая комментированность кода:** Пиши чистый, удобный, готовый к выпуску и максимально читаемый код на Python. Чтобы его можно было правит вручную, а не только агенту.
* **Экономия токенов:** Пиши код полными, логически завершенными модулями. Экономь токены codex, но не в ущерб читаемости и корректности кода.
* **Документирование и комментирование кода:** Документируй на русском языке кратко каждую функцию, класс, а также комментируй сложные места кода, подписывай секции кода.
Математические расчеты и сложные формулы **ОБЯЗАНЫ** иметь комментарии на русском языке, объясняющие *что* штрафуется и *почему*.
* Не связывать бизнес-логику оптимизатора напрямую с Django views, ORM, frontend или LLM.
* Optimization Engine должен быть отдельным Python-модулем с четкими входными и выходными моделями.

* **Целевая функция**
Не использовать одну "магическую" fitness-функцию без декомпозиции.

OptimizationResult обязан содержать разложение objective, например:
unassigned_penalty
sla_penalty
lateness_penalty
travel_time_penalty
overtime_penalty
workload_balance_penalty
plan_disruption_penalty
total_objective

* Все численные коэффициенты, ограничения и параметры алгоритмов ОБЯЗАНЫ находиться в отдельной классе-конфигурации.
* Рекомендуемые единицы: время — HH:MM, длительность и время в пути — минуты, расстояние — километры, координаты — широта/долгота. Для других единиц предпочтительно исопльзовать систему СИ.

# 5. Backend/API

Ты работаешь с Django REST Framework проектом. При написании и изменении кода строго следуй правилам ниже.

## Общие ограничения
1. Не изменяй существующие URL для взаимодействия с сущностями "инженер" и "заявка" (engineer, ticket/request) — маршруты должны остаться обратно совместимыми. Если новая функциональность требует изменения контракта существующего эндпоинта — сначала спроси, можно ли расширить/задеприкейтить, не меняя сам путь.

## Добавление нового поведения к существующим сущностям
2. Если нужно добавить нетипичное действие для сущности "инженер" или "заявка" (не CRUD), реализуй его через декоратор `@action` в соответствующем ViewSet. Не создавай отдельный ViewSet или router-запись под такие действия.

## Добавление новой сущности
3. Для новой сущности придерживайся следующего порядка и не пропускай шаги:
   1. Модель — добавь в `models.py` (миграции генерируй сразу же).
   2. Сериалайзеры — добавь нужные в `serializers.py` (отдельно под чтение/запись/список, если отличаются).
   3. ViewSet — добавь в `views.py`.
   4. Особые `@action`-методы — при необходимости, по тому же принципу, что и в п.2.

## Архитектурные требования к коду
4. Любую сложную бизнес-логику (валидация, вычисления, работа с несколькими моделями, side-эффекты) выноси в `services.py`, а не держи внутри сериалайзеров или view-методов. View и сериалайзер должны оставаться максимально "тонкими" — вызывать сервис, а не реализовывать логику самостоятельно.
5. Для всех ViewSet-ов используй миксин `MultiSerializerViewSet` (позволяет задавать разные сериалайзеры на разные actions/методы) — не переопределяй `get_serializer_class` вручную, если это можно решить через миксин.
6. Декоратор `@api_view` разрешен только для:
   - очень простых, самодостаточных эндпоинтов (без сложной логики, без нескольких связанных моделей);
   - селекторов (read-only агрегации/фильтрации данных).
   Для всего остального — используй ViewSet.

## Формат ответа
Когда добавляешь новую сущность или action — покажи изменения по каждому файлу отдельно (models → serializers → views → services, если применимо), с указанием, что именно добавлено/изменено, без урезания уже существующего кода в этих файлах.
