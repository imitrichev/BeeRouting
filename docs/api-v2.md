# API v2

Web-слой BeeRouting использует только `/api/v2/`. API v1 в текущем проекте
нет. Backend хранит состояние района и вызывает сервисы планирования; views и
serializers не содержат математическую логику.

## Запуск

```bash
.venv/bin/python backend/web_mvp/manage.py migrate
.venv/bin/python backend/web_mvp/manage.py runserver 8000
```

Все запросы к выбранному району передают `?territory=<territory_code>`. Район
создаётся при первой загрузке JSON и сохраняет собственный dataset, текущий
план, routing data и результат оптимизации. Переключение района не запускает
solver повторно.

## Основные endpoints

| Метод | URL | Результат |
|---|---|---|
| `GET` | `/api/v2/territories/` | Импортированные районы |
| `GET` | `/api/v2/dataset/?territory=...` | Dataset и сохранённый результат |
| `GET` | `/api/v2/dataset/official/` | Полная перезагрузка официальных районов |
| `POST` | `/api/v2/dataset/upload/` | Импорт JSON из multipart-поля `file` |
| `POST` | `/api/v2/optimize/?territory=...` | Расчёт Baseline или OR-Tools |
| `POST` | `/api/v2/sync-reference-statuses/?territory=...` | Только синхронизация reference-статусов |
| `POST` | `/api/v2/tasks/?territory=...` | Создание заявки |
| `POST` | `/api/v2/geocode/?territory=...` | Геокодирование адреса |
| `POST` | `/api/v2/replan/?territory=...` | Оперативное перепланирование |
| `POST` | `/api/v2/manual-reassignment/preview/?territory=...` | Проверка ручного переноса |
| `POST` | `/api/v2/manual-reassignment/confirm/?territory=...` | Подтверждение переноса |
| `POST` | `/api/v2/explain/<task_id>/?territory=...` | Объяснение результата |

CRUD-маршруты `engineers/`, `jobs/` и `reschedule-events/` зарегистрированы
через DRF Router. Read/write serializers разделены. Для новых действий
используется существующая v2-структура views и сервисов.

## Оптимизация

`POST /api/v2/optimize/` принимает JSON-параметры:

```json
{
  "solver": "ortools",
  "ignore_task_statuses": false,
  "preserve_assigned_tasks": false,
  "consider_equipment": false,
  "planning_time": "14:00",
  "operational_states": []
}
```

`solver` принимает `ortools` или `baseline`.

- В обычном режиме `CANCELLED` и `COMPLETED` исключаются из нового плана.
- `EN_ROUTE` и `IN_PROGRESS` фиксируются за `current_engineer_id`.
- `ASSIGNED` можно перенести, если не указан `preserve_assigned_tasks`.
- `NOT_SENT` и `OVERDUE` допускаются к планированию.
- `ignore_task_statuses=true` строит новый полный план по всем заявкам. Это
  отдельный режим утреннего перераспределения.
- `consider_equipment=true` включает количественный hard constraint для
  роутеров.

Операция сохраняет domain-снимок и синхронизирует ORM-модели инженеров и
заявок. Контрольный исполнитель из исходного CSV хранится отдельно от
текущего исполнителя рабочего плана.

## Перепланирование и ручной перенос

`POST /api/v2/replan/` принимает событие одного из типов:

- `EMERGENCY_TASK` — добавляет срочную аварийную заявку;
- `TASK_CANCELLED` — отменяет одну заявку и перестраивает только оставшуюся
  часть плана;
- `ENGINEER_UNAVAILABLE` — исключает инженера и возвращает его незакрытые
  заявки в очередь.

Закрытые и отменённые заявки сохраняются как история. Начатые заявки обычно
фиксируются; если инженер стал недоступен, они возвращаются в очередь, потому
что прежний исполнитель больше не может продолжить работу.

Ручной перенос выполняется в два запроса. Сначала `preview` проверяет навык,
транспорт, оборудование, окно, смену и результат короткой контрфактической
оптимизации. Ответ содержит `feasible`, причины отказа, `proposal_id`, число
инженеров и общий километраж до и после. Только затем `confirm` применяет
proposal. Устаревший или уже использованный proposal не принимается.

## Объяснение

`explain/<task_id>/` формирует фактический JSON из двух этапов:

1. дешёвая детерминированная проверка совместимости и вставки в маршрут;
2. короткий counterfactual-расчёт OR-Tools от текущего плана.

В JSON есть тип события, hard-причины, изменение пробега, времени,
задействованных инженеров, objective и количество изменений маршрута.
Поле `must_mention` помечает существенные факты. LLM, если настроена, получает
только этот JSON и формирует русский текст. При `BEEROUTING_MODE=production`
технический JSON во frontend не передаётся, остаётся только объяснение.

## Районы и хранение

Официальная перезагрузка удаляет сохранённое состояние официальных районов и
заново импортирует `Восток.json`, `Юго-восток.json` и `Югоцентр.json`.
Пользовательская загрузка добавляет или открывает район по `territory_code`.

По умолчанию используется SQLite, потому что это простой локальный MVP.
PostgreSQL совместим с ORM-моделями и нужен при одновременной работе нескольких
диспетчеров; PostGIS сейчас не обязателен. Снимок плана хранится в JSONField,
pickle не используется. Долгие расчёты пока выполняются синхронно.

## Ошибки

- `400` — некорректный JSON или параметры запроса;
- `404` — неизвестный район, заявка или адрес;
- `422` — domain/routing ошибка или невозможное действие;
- `502` — ошибка внешнего LLM-сервиса.

Все координаты, адреса и параметры времени должны пройти валидацию до вызова
solver. Подробная математическая логика описана в
[solver.md](solver.md), benchmark — в [benchmarks.md](benchmarks.md).
