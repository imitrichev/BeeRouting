# API v2 и сохранение районов

Frontend использует `/api/v2/`. Прежний `/api/` оставлен для совместимости.
Перед первым запуском выполните:

```bash
.venv/bin/python backend/web_mvp/manage.py migrate
```

Район появляется после загрузки JSON. `territory_code` — ключ района;
`territory_name` — подпись в списке. Повторная загрузка того же кода открывает
сохранённый район и не затирает существующий план. Для нового независимого
сценария нужен другой код территории.

- `GET territories/` — список импортированных районов.
- `POST dataset/upload/` — multipart JSON в поле `file`.
- `GET dataset/official/` — первая загрузка Югоцентра или открытие сохранённого.
- `GET dataset/?territory=...` — данные и сохранённый план, без оптимизации/OSRM.
- `POST optimize/?territory=...` — текущие параметры статусов и оперативного времени.
- `POST tasks/?territory=...` — создание заявки с нормативной длительностью.
- `POST geocode/?territory=...` — геокодирование.
- `POST replan/?territory=...` — авария, отмена или недоступность инженера.
- `POST manual-reassignment/preview/?territory=...` — проверка и сравнение метрик.
- `POST manual-reassignment/confirm/?territory=...` — подтверждение proposal_id.
- `POST explain/<task_id>/?territory=...` — объяснение через проверяемые факты и LLM.

Сохранение включает исходный контрольный JSON, актуальный domain-снимок,
матрицы, маршруты, метрики и геометрию. Снимок хранится в JSONField с явными
типами из белого списка; pickle не используется. Это позволяет восстановить
объяснения и продолжить планирование после перезапуска. ORM-модели инженеров
и заявок синхронизируются при сохранении; контрольный исполнитель хранится
отдельно от текущего. Изменения следует выполнять через операции сервиса,
а не напрямую менять ORM-записи: снимок является источником состояния плана.

Сервис создаётся отдельно для каждого запроса. Изменения и сохранение выполняются
в транзакции. Preview хранится в БД с версией района и становится недействительным
после изменения плана. Текущая БД остаётся SQLite для локального запуска;
модели совместимы с обычными полями PostgreSQL, PostGIS здесь не требуется.
SQLite не обеспечивает блокировку select_for_update: конкурентное использование
несколькими диспетчерами требует PostgreSQL. Продолжительные расчёты пока синхронны.

Из ветки коллеги взяты модели и связи территорий, районов, инженеров, заявок,
справочников и событий. Его старые обработчики оптимизации и дубли сериализаторов
не перенесены: API v2 использует актуальный сервис нашего проекта. Независимое
математическое ядро не импортирует Django.
