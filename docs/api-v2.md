# API v2

Веб-слой BeeRouting использует только `/api/v2/`. API v1 в текущем проекте
нет. Серверная часть хранит состояние района и вызывает сервисы планирования;
представления и сериализаторы не содержат математической логики.

## Запуск

```bash
.venv/bin/python backend/web_mvp/manage.py migrate
.venv/bin/python backend/web_mvp/manage.py runserver 8000
```

Все запросы к выбранному району передают `?territory=<territory_code>`. Район
создаётся при первой загрузке JSON и сохраняет собственный набор данных,
текущий план, маршрутные данные и результат оптимизации. Переключение района
не запускает решатель повторно.

## Основные методы API

| Метод | URL | Результат |
|---|---|---|
| `GET` | `/api/v2/territories/` | Импортированные районы |
| `GET` | `/api/v2/dataset/?territory=...` | Набор данных и сохранённый результат |
| `GET` | `/api/v2/dataset/official/` | Полная перезагрузка официальных районов |
| `POST` | `/api/v2/dataset/upload/` | Импорт JSON из multipart-поля `file` |
| `POST` | `/api/v2/optimize/?territory=...` | Расчёт Baseline или OR-Tools |
| `PATCH` | `/api/v2/jobs/status/?territory=...` | Изменить рабочий статус без запуска решателя |
| `POST` | `/api/v2/sync-reference-statuses/?territory=...` | Полная перезагрузка района и контрольного плана из официального JSON |
| `POST` | `/api/v2/tasks/?territory=...` | Создание заявки |
| `POST` | `/api/v2/geocode/?territory=...` | Геокодирование адреса |
| `POST` | `/api/v2/replan/?territory=...` | Оперативное перепланирование |
| `POST` | `/api/v2/manual-reassignment/preview/?territory=...` | Проверка ручного переноса |
| `POST` | `/api/v2/manual-reassignment/confirm/?territory=...` | Подтверждение переноса |
| `POST` | `/api/v2/explain/<task_id>/?territory=...` | Объяснение результата |

CRUD-маршруты `engineers/`, `jobs/` и `reschedule-events/` зарегистрированы
через маршрутизатор DRF. Сериализаторы чтения и записи разделены. Для новых
действий используется существующая структура представлений и сервисов API v2.

## Оптимизация

`POST /api/v2/optimize/` принимает JSON-параметры:

```json
{
  "solver": "ortools",
  "ignore_task_statuses": false,
  "preserve_assigned_tasks": false,
  "consider_equipment": false,
  "planning_time": "14:00",
  "operational_states": []
}
```

Параметр `solver` принимает значение `ortools` или `baseline`.

- В обычном режиме `CANCELLED` и `COMPLETED` исключаются из нового плана.
- `EN_ROUTE` и `IN_PROGRESS` фиксируются за `current_engineer_id`.
- `ASSIGNED` можно перенести, если не указан `preserve_assigned_tasks`.
- `NOT_SENT` и `OVERDUE` допускаются к планированию.
- `ignore_task_statuses=true` строит новый полный план без фиксации рабочих
  статусов. Это отдельный режим утреннего перераспределения, в котором
  участвуют в том числе `COMPLETED` и `CANCELLED`.
- `consider_equipment=true` включает количественное жёсткое ограничение для
  роутеров.

После `POST /api/v2/tasks/` новая заявка получает `NOT_SENT` и сразу
добавляется в `result.unassigned` с кодом `not_distribution_attempted` и
пояснением, что после её создания попыток распределения ещё не было. Текущий
план при этом сохраняется, а Baseline и OR-Tools не запускаются автоматически.

При запуске OR-Tools API сначала строит план на полных OSRM-матрицах. Для
`PUBLIC_TRANSPORT` исходный fallback равен автомобильному времени, умноженному
на два. Если настроен локальный OTP, сервис уточняет только вошедшие в маршрут
дуги по расписаниям наземного транспорта и метро Москвы и повторяет OR-Tools с
предыдущим планом как initial solution. Выполняется не более двух итераций. При
недоступности OTP, отсутствии маршрута или неудаче повторного поиска
сохраняется последний допустимый план.

Операция сохраняет снимок предметной модели и синхронизирует ORM-модели инженеров и
заявок. Контрольный исполнитель из исходного CSV хранится отдельно от
текущего исполнителя рабочего плана.

## Перепланирование и ручной перенос

`POST /api/v2/replan/` принимает событие одного из типов:

- `EMERGENCY_TASK` — добавляет срочную аварийную заявку;
- `TASK_CANCELLED` — отменяет одну заявку и перестраивает только оставшуюся
  часть плана;
- `ENGINEER_UNAVAILABLE` — исключает инженера и возвращает его незакрытые
  заявки в очередь.

Для событий `TASK_CANCELLED` и `ENGINEER_UNAVAILABLE` поле
`planning_time` больше не требуется: сервис определяет состояние из текущего
сохранённого плана. У отмены удаляется только соответствующая остановка, а
остальные назначенные заявки фиксируются. При недоступности перестраивается
часть маршрута недоступного инженера, чужие уже назначенные и начатые работы
сохраняются. Только `EMERGENCY_TASK` может свободно изменить существующие
назначения, потому что авария является форс-мажором.

Закрытые и отменённые заявки сохраняются как история. Начатые заявки
фиксируются за текущим исполнителем; при недоступности инженера его ещё не
закрытые заявки возвращаются в очередь для переназначения.

### Изменение статуса без перепланирования

`PATCH /api/v2/jobs/status/?territory=...` принимает:

```json
{"task_id": "J-100", "status": "IN_PROGRESS"}
```

Операция не вызывает Baseline, OR-Tools или перепланирование. Для заявки в
`ASSIGNED` или `OVERDUE` переход в `NOT_SENT` снимает исполнителя, удаляет
остановку из сохранённого маршрута и освобождает требуемое оборудование.
Расписание следующих остановок не сдвигается: высвободившееся время становится
перерывом инженера. Заявка появляется в `result.unassigned` с причиной
`manually_unassigned` и может участвовать в следующем ручном запуске решателя.
Начатые заявки `EN_ROUTE` и `IN_PROGRESS` таким способом освободить нельзя.
Если заявка не назначена, единственное допустимое ручное действие — перевод в
`CANCELLED`.

Ручной перенос выполняется в два запроса. Сначала `preview` проверяет навык,
транспорт, оборудование, окно, смену и результат короткой контрфактической
оптимизации. Ответ содержит `feasible`, причины отказа, `proposal_id`, число
инженеров и общий километраж до и после. Только затем `confirm` применяет
предложение с указанным `proposal_id`. Устаревшее или уже использованное
предложение не принимается.

## Объяснение

`explain/<task_id>/` формирует фактический JSON из двух этапов:

1. дешёвая детерминированная проверка совместимости и вставки в маршрут;
2. короткий контрфактический расчёт OR-Tools на основе текущего плана.

В JSON есть тип события, причины нарушения жёстких ограничений, изменение
пробега, времени, числа задействованных инженеров, значения целевой функции и
количества изменений маршрута.
Поле `must_mention` помечает существенные факты. LLM, если настроена, получает
только этот JSON и формирует русский текст. При `BEEROUTING_MODE=production`
технический JSON не передаётся клиентскому приложению: пользователь видит
только объяснение.

## Районы и хранение

Официальная перезагрузка удаляет сохранённое состояние официальных районов и
заново импортирует `Восток.json`, `Юго-восток.json` и `Югоцентр.json`.
Пользовательская загрузка добавляет или открывает район по `territory_code`.

По умолчанию используется SQLite, потому что это простой локальный MVP.
PostgreSQL совместим с ORM-моделями и нужен при одновременной работе нескольких
диспетчеров; PostGIS сейчас не обязателен. Снимок плана хранится в JSONField,
pickle не используется. Долгие расчёты пока выполняются синхронно.

## Ошибки

- `400` — некорректный JSON или параметры запроса;
- `404` — неизвестный район, заявка или адрес;
- `422` — ошибка предметных или маршрутных данных либо невозможное действие;
- `502` — ошибка внешнего LLM-сервиса.

Все координаты, адреса и параметры времени должны пройти валидацию до вызова
решателя. Подробная математическая логика описана в
[документе об оптимизации](optimization.md), а проверки производительности —
в [документе о бенчмарках](benchmarks.md).
