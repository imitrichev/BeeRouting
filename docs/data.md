# Тестовые данные BeeRouting

## Состав набора

В проекте используются три набора заявок, соответствующие территориям
«Югоцентр», «Восток» и «Юго-восток». Для каждой территории в корне репозитория
хранятся:

- `<Район> Синтетические данные.csv` — исходный набор заявок, выданный
  организаторами;
- `<Район> Контрольное распределение_old.csv` — исходное контрольное
  распределение организаторов;
- `<Район> Контрольное распределение.csv` — скорректированное командой
  контрольное распределение;
- `<Район>_old.json` — сценарий, собранный с исходным контрольным
  распределением;
- `<Район>.json` — актуальный сценарий со скорректированным распределением.

Суффикс `_old` относится к исходному контрольному распределению, а не к
исходным заявкам: актуальный и `_old` JSON строятся на одном синтетическом
наборе заявок. В контрольных CSV содержатся назначенная бригада, статус и
порядок заявок. В вариантах без `_old` назначения и последовательности были
исправлены командой так, чтобы маршруты соблюдали действующие жёсткие
ограничения: квалификацию, транспорт, оборудование, временные окна и смены.
Поэтому
актуальное распределение используется для проверки допустимости и сравнения
решателей, а `_old` сохранено для воспроизводимости исходных материалов.

Итоговый JSON генерируется из синтетического CSV, общего `engineers.csv` и
соответствующего контрольного CSV. Готовый JSON не используется как источник
для собственной перегенерации:

```bash
.venv/bin/python -m backend.optimization.scripts.generate_dataset_json
```

## Поля заявок

Исходный набор организаторов содержит идентификатор заявки, типы заявки BK и
HD, начало и окончание временного окна, район, адрес, признаки подключения и
гигабитного подключения. В рабочие синтетические CSV команда добавила колонку
`Требуемое количество роутеров, шт.`. При генерации JSON сведения
нормализуются и дополняются следующими полями:

| Поле | Назначение |
|---|---|
| `job_id`, `request_id` | Идентификатор заявки в сценарии |
| `control_request_id` | Идентификатор соответствующей строки контрольного распределения |
| `territory_code`, `territory_name`, `district` | Территория и район заявки |
| `request_type_bk`, `request_type_hd` | Исходные классификаторы работ |
| `address`, `lat`, `lon` | Нормализованный адрес и координаты WGS84 |
| `window_start`, `window_end` | Допустимое окно начала работы |
| `duration_min`, `time_norm_code` | Длительность работы и код норматива |
| `skill_required` | Требуемая квалификация инженера |
| `priority` | `urgent` для аварии, `normal` для остальных работ |
| `required_vehicle` | Обязательный транспорт; `null`, если отдельного требования нет |
| `required_router_count` | Количество роутеров, необходимое для заявки |
| `reference_status`, `reference_crew`, `reference_sequence` | Контрольные статус, исполнитель и порядок выполнения |
| `gigabit` | Признак гигабитного подключения |

Все аварийные заявки принудительно получают приоритет `urgent`, включая импорт
старых JSON, где мог быть указан обычный приоритет.

## Инженеры и файл `engineers.csv`

Исходные синтетические наборы описывают заявки, но не содержат полного
машиночитаемого профиля каждого инженера. Поэтому команда создала единый
справочник `engineers.csv`. Он связывает бригады трёх территорий с их
квалификациями, способом передвижения, стартовой точкой, сменой и запасом
оборудования. Генератор выбирает строки по `territory_code` и встраивает их в
соответствующий JSON.

Структура файла:

| Поле | Назначение |
|---|---|
| `territory_code` | Код территории: `yugo_tsentr`, `vostok` или `yugo_vostok` |
| `engineer_id` | Стабильный уникальный идентификатор инженера |
| `name` | Имя инженера или название бригады, совпадающее с контрольными данными |
| `vehicle_type` | `car`, `foot`, `bicycle` или `public_transport` |
| `skills` | Коды квалификаций через `|` |
| `start_address`, `start_lat`, `start_lon` | Адрес и координаты начала маршрута |
| `shift_start`, `shift_end` | Начало и конец доступной смены |
| `available_router_count` | Доступный инженеру утренний запас роутеров |

Следующие характеристики не были предоставлены как полный готовый справочник
организаторами и сформированы командой для работы математической модели:

- квалификации каждого инженера (`skills`);
- тип транспорта каждого инженера (`vehicle_type`);
- количество доступных инженеру роутеров (`available_router_count`);
- количество роутеров, требуемых каждой заявке (`required_router_count`).

Стартовые точки и рабочие смены также сведены в `engineers.csv`; для удалённых
бригад используются отдельные старты, например Ступино и Кашира. Границы смен
заданы с точностью до часа, продолжительность смены не превышает 12 часов.

## Справочники и производные значения

Типы работ преобразуются в коды квалификаций и нормативов генератором. В
сценарии используются квалификации `local_works`, `connection_orders` и
`emergency_works`, типы транспорта `car`, `foot`, `bicycle` и
`public_transport`, а также приоритеты `normal` и `urgent`.

Нормативы из `backend/optimization/work_norms.py`:

| Тип работ | Полный норматив | Работа после прибытия |
|---|---:|---:|
| Подключение клиентов | 90 мин | 70 мин |
| Авария на ТКД | 100 мин | 80 мин |
| Дозаказ оборудования | 40 мин | 20 мин |
| Локальная заявка/ремонт | 50 мин | 30 мин |

Из полного норматива вычитается 20 минут резервной дороги, а в `duration_min`
записывается только работа после прибытия. Фактическое время в пути алгоритм
получает от поставщика маршрутных данных, поэтому оно не обязано равняться
этому резерву.

## Единицы измерения

- временные окна и границы смен — `HH:MM`;
- длительность работы и время движения — минуты;
- расстояние — километры;
- координаты — широта и долгота WGS84;
- оборудование — целое количество роутеров.

Эти единицы также записаны в объекте `units` каждого JSON.

## Геокодирование

Адреса офиса, стартовых точек инженеров и заявок нормализуются через Nominatim.
Генератор сначала проверяет постоянный `nominatim_cache.json`, затем локальный
адрес `http://127.0.0.1:8080/search`, а при его недоступности может обратиться
к публичному Nominatim. В кэше сохраняются координаты и исходный
`display_name`; в сценарий попадают этот нормализованный адрес и координаты.

При нескольких результатах выбирается вариант, ближайший к офису территории.
Нераспознанный адрес получает заметную резервную координату Кремля и попадает в
`geocoding_warnings`, чтобы ошибку нельзя было пропустить при проверке набора.

## Принятые допущения

- каждый инженер относится к одной территории, имеет один тип транспорта и
  может обладать несколькими квалификациями;
- запас роутеров задаётся на начало дня, не пополняется и не передаётся между
  инженерами;
- `required_vehicle = null` означает отсутствие обязательного типа транспорта,
  а не отсутствие транспорта у исполнителя;
- временное окно ограничивает начало работы; завершение должно укладываться в
  смену инженера;
- возвращение на стартовую точку после последней заявки не требуется;
- контрольное распределение служит ориентиром для проверки и бенчмарка, но не
  ограничивает решатель при построении нового плана;
- координаты и адреса, полученные геокодированием, необходимо визуально
  проверять перед промышленным использованием.

Для детерминированной матрицы без OSRM приняты средние скорости: автомобиль —
30 км/ч, общественный транспорт — 15 км/ч, велосипед — 15 км/ч, пешком —
5 км/ч. Автомобильная скорость выбрана как приближение к опубликованной
[средней скорости движения автомобилей в Москве](https://cars.ru/post/deptrans-v-moskve-vyrosla-srednyaya-skorost-dvizheniya-mashin).
При использовании OSRM время берётся из дорожного графа. Для общественного
транспорта стандартный OSRM не учитывает расписания, поэтому используется
автомобильный граф с удвоенным временем движения.
