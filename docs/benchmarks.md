# Benchmarks Optimization Engine

В проекте есть три benchmark-сценария. Они измеряют текущее время работы и
качество маршрутов, но не являются unit-тестами и не содержат требования
вроде «решение обязано быть найдено быстрее N секунд». Результат зависит от
процессора, версии библиотек, лимита solver и выбранного источника матриц.

Все команды ниже запускаются из корня проекта.

## Окружения

Для OR-Tools, Baseline и web-зависимостей используется основное окружение:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Timefold устанавливается отдельно, потому что Python API Timefold требует
Python 3.10–3.12 и JVM. Текущий проект проверен с Python 3.12 и JDK 21:

```bash
python3.12 -m venv .timefold-venv
.timefold-venv/bin/python -m pip install \
  -r backend/optimization/requirements-timefold.txt
```

При запуске Timefold необходимо указать Java. Если подходящая Java уже есть в
`PATH`, переменные можно не задавать:

```bash
JAVA_HOME="$PWD/.tools/jdk-21.0.2" \
PATH="$JAVA_HOME/bin:$PATH" \
PYTHONPATH="$PWD" \
.timefold-venv/bin/python -m backend.optimization.benchmarks.benchmark_yugo_center
```

## Маленький OR-Tools benchmark

Файл: `backend/optimization/benchmarks/benchmark_ortools.py`.

Сценарий содержит 3 инженеров и 5 заявок. Матрицы заданы вручную, поэтому
результат не зависит от сети или OSRM. Этот benchmark нужен для быстрого
наблюдения за накладными расходами вызова OR-Tools на маленькой задаче.

```bash
.venv/bin/python -m backend.optimization.benchmarks.benchmark_ortools
```

Число измерений после прогрева задаётся параметром:

```bash
.venv/bin/python -m backend.optimization.benchmarks.benchmark_ortools \
  --iterations 50
```

Перед измерениями выполняется один прогревочный запуск. Он не входит в
статистику. На экран выводятся общее время, среднее, медиана, минимум и
максимум. Benchmark измеряет только `ORToolsOptimizer.optimize()` и не
учитывает загрузку JSON, построение матриц и web API.

## Крупный синтетический OR-Tools benchmark

Файл: `backend/optimization/benchmarks/benchmark_ortools_large.py`.

Сценарий содержит 15 инженеров и 100 заявок. Матрицы времени и расстояния
строятся детерминированно в памяти. Все заявки требуют `LOCAL_WORKS`, все
инженеры используют `CAR`. Этот benchmark показывает поведение OR-Tools на
более крупной, но полностью воспроизводимой задаче.

```bash
.venv/bin/python -m backend.optimization.benchmarks.benchmark_ortools_large \
  --iterations 1
```

Первый запуск также используется для прогрева и не входит в измерения.
Внутренний лимит OR-Tools в этом сценарии задаётся в коде через
`OptimizerConfig(time_limit_minutes=5)`. Фактическое завершение может быть
раньше лимита, если solver закончит поиск.

## Сравнительный benchmark «Югоцентр»

Файл: `backend/optimization/benchmarks/benchmark_yugo_center.py`.

Это основной демонстрационный benchmark. Он загружает `Югоцентр.json` и
сравнивает пять вариантов, если включены оба дополнительных solver'а:

1. контрольное распределение составителей из CSV;
2. `GreedyBaselineOptimizer` — заявки и инженеры перебираются во входном
   порядке, глобальная оптимизация не выполняется;
3. `ORToolsOptimizer` — основной solver проекта;
4. `ICOOptimizer` — экспериментальный solver на основе ICO-DE и random keys;
5. `TimefoldOptimizer` — дополнительный solver для сравнения подходов.

Baseline и OR-Tools запускаются всегда. ICO-DE подключается флагом
`--include-ico-de`, а Timefold — флагом `--include-timefold`. Поэтому без этих
флагов benchmark фактически сравнивает контрольный план, Baseline и OR-Tools.

Benchmark печатает:

- время расчёта;
- число назначенных и неназначенных заявок;
- число реально задействованных инженеров;
- общий пробег и время движения;
- компоненты objective и итоговое значение;
- процентные изменения относительно Baseline и контрольного плана;
- пробег каждого инженера.

Перед выводом benchmark проверяет статусный контракт всех запущенных solver'ов.
В статусном режиме завершённые и отменённые заявки не должны попасть
в новый маршрут, а заявки `EN_ROUTE` и `IN_PROGRESS` должны остаться у своего
инженера и быть первой активной точкой его маршрута.

### Детерминированная координатная матрица

```bash
JAVA_HOME="$PWD/.tools/jdk-21.0.2" \
PATH="$JAVA_HOME/bin:$PATH" \
PYTHONPATH="$PWD" \
.timefold-venv/bin/python \
  -m backend.optimization.benchmarks.benchmark_yugo_center \
  --routing-provider coordinate \
  --iterations 1
```

`coordinate` вычисляет расстояние по координатам и переводит его во время с
демонстрационной скоростью 30 км/ч. Дорог, одностороннего движения и реального
транспортного графа в этом режиме нет. Его преимущество — воспроизводимость и
отсутствие сетевых запросов.

### Реальные дорожные матрицы OSRM

```bash
JAVA_HOME="$PWD/.tools/jdk-21.0.2" \
PATH="$JAVA_HOME/bin:$PATH" \
PYTHONPATH="$PWD" \
.timefold-venv/bin/python \
  -m backend.optimization.benchmarks.benchmark_yugo_center \
  --routing-provider osrm \
  --iterations 1 \
  --osrm-timeout-seconds 30
```

В режиме `osrm` время импорта включает получение или чтение из кэша матриц.
Время solver в строке «Время расчёта» не включает построение матриц: оно
печатается отдельно как «Импорт и построение матриц». Результат может зависеть
от доступности OSRM, его версии, профилей транспорта и содержимого кэша.

### Два режима обработки статусов

Без дополнительных флагов учитываются статусы dataset:

- `CANCELLED` и `COMPLETED` остаются историей и исключаются из нового плана;
- `EN_ROUTE` и `IN_PROGRESS` закрепляются за текущим инженером;
- `ASSIGNED` можно перенести для улучшения плана;
- `NOT_SENT` и `OVERDUE` планируются;
- `--preserve-assigned` дополнительно запрещает перенос `ASSIGNED`.

Полное перераспределение запускается флагом `--ignore-task-statuses`:

```bash
JAVA_HOME="$PWD/.tools/jdk-21.0.2" \
PATH="$JAVA_HOME/bin:$PATH" \
PYTHONPATH="$PWD" \
.timefold-venv/bin/python \
  -m backend.optimization.benchmarks.benchmark_yugo_center \
  --routing-provider coordinate \
  --iterations 1 \
  --ignore-task-statuses
```

В полном режиме все 56 заявок «Югоцентра» становятся входом нового плана,
включая строки с историческими статусами. Текущие исполнители и статусы не
фиксируются. Этот режим соответствует включённому по умолчанию переключателю
«Игнорировать статусы и перераспределить все заявки» во frontend.

### Параметры сравнительного benchmark

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `--path` | `Югоцентр.json` | JSON-сценарий |
| `--control-csv` | `Югоцентр Контрольное распределение..csv` | Ручной контрольный план |
| `--routing-provider` | `coordinate` | `coordinate` или `osrm` |
| `--iterations` | `3` | Число измеряемых запусков каждого solver |
| `--time-limit-minutes` | `1` | Лимит одного запуска OR-Tools |
| `--timefold-time-limit-seconds` | `20` | Лимит поиска Timefold |
| `--osrm-timeout-seconds` | `30` | Тайм-аут одного запроса OSRM |
| `--preserve-assigned` | выключен | Фиксация заявок `ASSIGNED` |
| `--ignore-task-statuses` | выключен | Полное перераспределение всех заявок |
| `--consider-equipment` | выключен | Учитывать суммарный расход роутеров по маршруту инженера |
| `--include-ico-de` | выключен | Добавить экспериментальный ICO-DE в сравнение |
| `--include-timefold` | выключен | Добавить Timefold, если доступны Python API и Java |

Baseline и OR-Tools выполняются всегда. ICO-DE и Timefold по умолчанию не
запускаются, чтобы обычный benchmark оставался коротким. Если указан
`--include-timefold`, но Java или Python API Timefold недоступны, benchmark
печатает причину и оставляет в таблице прочерк вместо Timefold; Baseline и
OR-Tools при этом продолжают выполняться.

Например, сравнение всех доступных вариантов:

```bash
.venv/bin/python -m backend.optimization.benchmarks.benchmark_yugo_center \
  --include-ico-de --include-timefold \
  --routing-provider osrm --iterations 1
```

Baseline и OR-Tools сначала запускаются один раз для прогрева, после чего
измеряются `--iterations` раз. Timefold измеряется вместе с холодным запуском
JVM и генерацией Java-классов constraint streams. Поэтому его строку времени
нельзя напрямую трактовать как чистое время локального поиска. Лимит 20 секунд
ограничивает поиск, но не запуск JVM, построение модели и преобразование
результата; фактическое измерение закономерно больше 20 секунд.

### Последний полный запуск

Команда:


### Последний полный запуск с OSRM

OSRM не является отдельным benchmark-файлом. Это второй routing-режим того же
`benchmark_yugo_center.py`, который включается параметром
`--routing-provider osrm`. Baseline, OR-Tools и Timefold получают одну и ту же
заранее построенную для сценария совокупность матриц, но время движения
выбирается по типу транспорта конкретного инженера.

Команда:

```bash
JAVA_HOME="$PWD/.tools/jdk-21.0.2" \
PATH="$JAVA_HOME/bin:$PATH" \

  -m backend.optimization.benchmarks.benchmark_yugo_center \
  --routing-provider osrm \
  --iterations 1 \
  --osrm-timeout-seconds 30 \
  --ignore-task-statuses
```

Время построения матриц общее для всех трёх вариантов и не прибавляется к

инженеров и сократил пробег Baseline на 38.45%. Timefold также назначил все

секунд.

Контрольное распределение снова не включено в таблицу допустимых решений: на
дорожных матрицах OSRM обнаружено 6 нарушений hard constraints — 3 нарушения
временных окон и 3 выхода за окончание смены. CSV и JSON при этом согласованы;
прочерк означает недопустимость расписания, а не отсутствие контрольных
данных.

Этот результат получен через публичные OSRM endpoints и локальный кэш
provider. При очистке кэша или изменении OSRM-графа значения могут немного
измениться. Для воспроизводимой защиты разумно заранее прогреть кэш тем же
dataset и не менять routing endpoints между сравниваемыми запусками.

### Постоянный кэш OSRM

В web API и benchmark OSRM-provider автоматически использует:

- `.cache/osrm/osrm_pairs.sqlite3` — направленные пары точек в SQLite;
- `.cache/osrm/matrices/<сигнатура>.npz` — полные матрицы для конкретного
  дорожного графа и упорядоченного набора координат.

Порядок чтения: память процесса → NPZ → SQLite → OSRM для недостающих пар.
SQLite позволяет повторно использовать точки в другом порядке и в другом
dataset. Запрос недостающих пар выполняется прямоугольной Table-матрицей;
она может захватывать уже известные пары, но их сохранённые значения не
перезаписываются. Полный повторный запуск читает NPZ без HTTP Table-запросов.

Ключ включает endpoint и профиль графа, точные координаты и версию формата.
Направления A→B и B→A различаются. В кэше хранятся исходные секунды и метры
OSRM; преобразование в минуты/километры и коэффициент PUBLIC_TRANSPORT
применяются после чтения. Поэтому изменение коэффициента не использует
устаревшее округлённое время. Внутри solver остаются минуты и километры.

Пути переопределяются через `OSRM_PAIR_CACHE_PATH` (файл SQLite) и
`OSRM_MATRIX_CACHE_PATH` (каталог NPZ). Значение `off` отключает соответствующий
уровень. Например, запуск без постоянного кэша:

```bash
OSRM_PAIR_CACHE_PATH=off OSRM_MATRIX_CACHE_PATH=off \
.venv/bin/python -m backend.optimization.benchmarks.benchmark_yugo_center \
  --routing-provider osrm --iterations 1 --ignore-task-statuses
```

Кэш включён только у OSRM: coordinate и in-memory provider его не используют.
Он общий для OR-Tools, Baseline и Timefold, поскольку все получают матрицы
через routing-слой. Кэш сокращает подготовку входа, но не поиск solver или
запуск JVM. GeoJSON-геометрия по-прежнему кэшируется только в памяти процесса.

Автоматического срока истечения нет. После обновления дорожного графа по тому
же endpoint нужно очистить оба уровня или задать новые пути. Старые файлы
`osrm_pair_cache.sqlite` и `route_matrix_cache.npz` справочного скрипта не
импортируются: в их ключах недостаточно сведений об источнике маршрутизации.
Повреждённый NPZ восстанавливается из SQLite или HTTP. Отсутствующие маршруты
и ошибочные ответы не записываются как успешные данные.

Проверка на полном Югоцентре (56 заявок, OSRM, один замер): импорт и
подготовка матриц при заполнении кэша заняли **10.982820 с**, при повторном
запуске в новом процессе — **0.016634 с**. Во втором запуске HTTP был
принудительно запрещён тестовой подменой `urlopen`; benchmark завершился
успешно. OR-Tools в обоих случаях назначил 56 заявок, задействовал 6 инженеров
и получил 188.313 км, 791 минуту движения. Собственно поиск занял 0.944933 с
и 0.904611 с соответственно: основное ускорение относится к подготовке матриц.
Timefold в этой проверке не запускался: использовалось основное `.venv`.

Основными метриками качества по ТЗ являются количество задействованных
инженеров и пробег. Перед их сравнением нужно проверить, что планы назначили
одинаковое количество заявок. План с меньшим пробегом, полученным за счёт
пропуска заявок, не является лучшим: это отражается большим
`unassigned_penalty`.

`total_objective` сравним только между запусками с одной конфигурацией весов и
одним набором заявок. Нельзя напрямую сравнивать objective статусного режима
на 14 заявках и полного режима на 56 заявках.

Микросекундные различия Baseline и маленького OR-Tools benchmark сильно
зависят от фоновой нагрузки системы. Для презентации важнее показывать
назначенные заявки, число инженеров, пробег и декомпозицию objective, а время
приводить вместе с лимитами solver и указанием холодного запуска JVM.
