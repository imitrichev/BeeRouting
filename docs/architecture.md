# Архитектура BeeRouting

## Краткая схема решения

```text
Интерфейс (Vue 3, Vuetify, MapLibre)
              |
              v
API v2 (Django REST Framework)
              |
              v
Сервисный слой и адаптер сценария
              |
              v
Алгоритм планирования
(Baseline / OR-Tools / ICO-DE / Timefold)
              |
              v
Данные сценария и результаты
(SQLite, JSON/CSV, матрицы OSRM и уточнения OTP)
```

Интерфейс загружает состояние выбранной территории через `/api/v2/`, запускает
расчёт и отображает маршруты, назначения и причины, по которым заявки остались
нераспределёнными. Django API отвечает за HTTP-контракт, хранение состояния и
вызов сервисного слоя; бизнес-логика не размещается в представлениях и
сериализаторах.

Сервисный слой преобразует сохранённый сценарий в независимые от Django
предметные модели `OptimizationProblem`. Решатель получает инженеров, заявки и
готовые матрицы времени и расстояния, а возвращает `OptimizationResult`.
Результат сохраняется в SQLite и передаётся интерфейсу. Геометрию дорог и
матрицы для реального расчёта предоставляет OSRM; воспроизводимые тесты могут
использовать детерминированный координатный поставщик маршрутных данных.

Для инженеров на общественном транспорте сервисный слой выполняет итерационное
уточнение. Первый план OR-Tools строится на полной fallback-матрице
`автомобильное время OSRM × 2`. Затем локальный OpenTripPlanner рассчитывает по
московскому GTFS только фактически используемые дуги с учётом времени
отправления, наземного транспорта и метро. После обновления матрицы OR-Tools
получает предыдущий план как initial solution; цикл ограничен двумя итерациями.
Недоступность OTP или отсутствие маршрута оставляет fallback без изменений.

Подробное описание алгоритмов, целевой функции, метрик, жёстких и мягких
ограничений приведено в [документации по оптимизации](optimization.md).
Состав и происхождение входных файлов описаны в [документации по
данным](data.md), HTTP-контракт — в [описании API v2](api-v2.md).
