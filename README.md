# BeeRouting

BeeRouting — веб-сервис для планирования маршрутов выездных
инженеров по кейсу Бизнес-3 «Интеллектуальный сервис планирования рабочих маршрутов» хакатона "Лидеры цифровой транфсформации".

Он дает возможность автоматически распределять заявки между инженерами,
выстраивать маршруты с учетом порядка посещения на карте, переназначать заявку
вручную, учитывае три возможные ситуации перепланирования.
Также он помогает диспетчеру понять, почему заявка назначена или осталась без
исполнителя.

В соответствии с техническим заданием, проект ориентирован на 10–15
инженеров, до 100 заявок, временные окна заявок (по умолчанию -двухчасовые),
различающиеся навыки инженеров и транспорт,
перепланирование в течение рабочего дня и сравнение с простым жадным
алгоритмом (baseline).

Готовая версия BeeRouting развёрнута по адресу: **<https://beerouting.ru>**.

## Фичи проекта

- загрузка трёх официальных районов и пользовательских JSON;
- отдельное хранение плана каждого района, поэтому переключение района не
  требует повторной оптимизации;
- Возможность сравнения с Baseline (жадный алгоритм);
- основной `ORToolsOptimizer` на Google OR-Tools;
- экспериментальный `ICOOptimizer` на ICO-DE и дополнительный
  `TimefoldOptimizer` для сравнения;
- проверка контрольного распределения на допустимость;
- бенчмарки для сравнения решателей;
- новое контрольное распределение (не из датасета организаторов) без
  противоречий для сравнений (3 бенчмарка + возможность загрузки через
  фронтенд);
- временные окна, рабочие смены, квалификации как жёсткие ограничения;
- возможность учитывать тип транспорта как жёсткое ограничение;
- опциональный учёт количества роутеров у инженера;
- расчёт времени движения и расстояния отдельно для каждого типа транспорта;
- OSRM-матрицы и дорожная геометрия маршрута для MapLibre;
- три события перепланирования: срочная заявка, отмена заявки и
  недоступность инженера;
- ручное переназначение с предварительной проверкой, причинами отказа и
  подтверждением изменения метрик;
- создание заявки через интерфейс с геокодированием адреса и нормативной
  длительностью;
- статусы заявок, фиксация уже начатых работ и сохранение плана в БД;
- двухступенчатые структурированные объяснения решения + генерация по ним
  связного текста (отчета) через LLM.

## Соответствие ТЗ

| Требование | Реализация |
|---|---|
| Распределить заявки и определить порядок визитов | OR-Tools, Baseline, ICO-DE, Timefold |
| Навык заявки входит в навыки инженера | Hard constraint; используются `LOCAL_WORKS`, `CONNECTION_AND_UPSELL`, `EMERGENCY_WORKS` |
| Работа укладывается в смену | Hard constraint с учётом дороги, ожидания и длительности работы |
| Начало работы попадает в окно | Hard constraint; ранний приезд допускает ожидание |
| Тип транспорта | Один из `CAR`, `WALK`, `BICYCLE`, `PUBLIC_TRANSPORT`; матрицы выбираются по инженеру |
| Оборудование | Дополнительный hard constraint; для роутеров учитывается количество, режим можно выключить |
| Обязательные метрики | Число задействованных инженеров и пробег по каждому инженеру и суммарно |
| Показать маршрут на карте | MapLibre, OSRM geometry; старт маршрута — стартовая точка инженера |
| Неназначенные заявки | `unassigned_task_ids` и структурированная причина по каждой заявке |
| Перепланирование | События аварии, отмены и недоступности инженера |
| Объяснение решения | Детерминированные проверки, counterfactual-проверка и LLM-текст |

Возврат на стартовую точку после последней заявки не требуется, как указано в ТЗ.

## Установка и запуск

Проверить BeeRouting без локальной установки можно на сайте
**<https://beerouting.ru>**. Ниже приведена инструкция для запуска проекта на
своём компьютере.

### Что понадобится

- Linux или macOS (для Windows рекомендуется WSL 2);
- Python 3.10 или новее;
- Node.js 20 или новее и npm 10 или новее;
- доступ в интернет для установки зависимостей и обращения к публичным
  сервисам маршрутизации;
- Docker — только если вы хотите поднять локальные Nominatim и
  OpenTripPlanner.

Все команды ниже выполняются из корня репозитория.

### 0. Клонирование репозитория

Клонировать репозиторий
```bash
git clone https://git@git.sourcecraft.dev/lct-hackaton-2026/case-13-field-engineer-routing-team-30.git
cd case-13-field-engineer-routing-team-30
```

### 1. Установка backend

Создайте виртуальное окружение Python, установите зависимости и примените
миграции базы данных:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python backend/web_mvp/manage.py migrate
```

Дополнительные сведения о web-слое и его режимах приведены в
[README Django web MVP](backend/web_mvp/README.md).

Для генерации человекочитаемых удобных отчетов из структурироаных данных при
объяснении причин назначения используется LLM GigaChat.

Необходимо разместить ключ Authorization key от GigaChat в файле `LLM/.env`.
Пример файла:

```dotenv
GIGACHAT_AUTH_KEY=...
```

### 2. Запуск backend

```bash
.venv/bin/python backend/web_mvp/manage.py runserver 8000
```

API будет доступен по адресу <http://127.0.0.1:8000/api/v2/>. Не закрывайте
этот терминал до окончания работы с приложением.

### 3. Установка и запуск клиентского приложения

Для клиентского приложения требуются Node.js 20+ и npm 10+. Откройте второй
терминал, перейдите в каталог `client/` и установите зависимости:

```bash
cd client
npm install
```

Создайте в этом каталоге файл `.env`:

```dotenv
VITE_API_URL=http://127.0.0.1:8000
```

Запустите клиентское приложение в режиме разработки:

```bash
npm run dev
```

После запуска откройте <http://localhost:5173>. Клиент будет обращаться к
запущенному Django API по адресу из `VITE_API_URL`.

Для проверки production-сборки выполните:

```bash
npm run build
```

Подробное описание переменных окружения, команд, структуры клиента и возможных
проблем приведено в [README клиентского приложения](client/README.md).

### 4. Загрузка демонстрационных данных

В интерфейсе нажмите «Перезагрузить официальный датасет». Приложение загрузит
актуальные данные районов «Восток», «Юго-восток» и «Югоцентр». После этого
можно запустить жадный Baseline или основной алгоритм OR-Tools и сравнить
полученные маршруты.

### Сценарий демонстрации с перепланированием

1. Нажмите «Перезагрузить официальный датасет». Это очищает сохранённое
   состояние и заново загружает три района.
2. Выберите район (например, "Юго-Центр") в списке. Каждый район хранит
   собственный результат.
3. Нажмите в верхнем меню кнопку "Назначить заявки". Выберите
   `Baseline (жадный алгоритм)`, чтобы запустить простое планирование жадным
   алгоритмом.

   Галочку "Учитывать оборудование" оставьте отмеченной.

   Вы получите результат:

   - Инженеров: 11
   - Заявок: 45
   - Пробег, км: 325.1

4. Теперь нажмите "Сбросить изменения" и повторите действие "Назнчаить заявки"
   только с решателем `OR-Tools`.

   Вы получите результат:

   - Инженеров: 10
   - Заявок: 56
   - Пробег, км: 155.4

   Этот результат значительно лучше: на 11 больше назначенных заявок и общий
   пробег снизился более, чем в два раза.
5. Выберите инженера или флажок на карте. Серые точки становятся цветными,
   показывается маршрут инженера, порядок обхода заявок. Офис отмечен домиком.
6. Выберите действие "Запросить объяснение" у заявки (значок "i"). Будет
   сделан запрос к LLM и показано объяснение.
7. В верхнем меню нажмите «Перепланирование». Выберите инженера "Переладов
   Алексей" и запустите перепланирование.

   Алгоритм сможет распределить заявки без нарушений жестких ограничений с
   привлечением дополнительного инженера.

   Инженеров по прежнему останется 10, а назначенных заявок 56

   Пробег составит 189.1 км.

8. Далее выберите, например, заявку `yugo_tsentr-J32840` в списке заявок под
   картой и нажмите на значок с человечком - переназначение заявки вручную.

   При выборе нового исполнителя интерфейс отразит причины невозможности
   назначения или старые и новые метрики, если переназначение допустимо. А
   отдельное подтверждение изменит план.

Кнопка «Контрольное распределение» отбрасывает текущее состояние выбранного
района, заново читает его официальный JSON и восстанавливает контрольные
назначения, порядок и статусы. Диспетчер меняет operational-статус заявки
через выпадающий список без запуска solver: у назначенной заявки доступны
«Назначена в плане», «В пути», «В работе», «Выполнена» и «Отменена», а у
неназначенной — только «Отменена».

## Установка дополнительных локальных сервисов

Для установки локальных Nominatim и OpenTripPlanner нужен Docker. Скрипт
скачивает OSM- и GTFS-данные, поэтому выполнение потребует нескольких гигабайт
свободного места и может занять продолжительное время:

```bash
bash install.sh
```

После запуска Nominatim будет доступен на порту `8080`, а OpenTripPlanner — на
порту `8081`. Сам OSRM этот скрипт не запускает: без дополнительной настройки
BeeRouting продолжит использовать публичные OSRM-сервисы, перечисленные выше.

### Режим production

Чтобы скрыть от пользователя технический JSON объяснений, запустите backend
с переменной окружения:

```bash
BEEROUTING_MODE=production \
  .venv/bin/python backend/web_mvp/manage.py runserver 8000
```

Команда `runserver` предназначена только для разработки и локальной
демонстрации. При развёртывании на сервере Django следует запускать через
WSGI/ASGI-сервер, а собранный frontend отдавать через веб-сервер.

## Данные и геокодирование

Подробное описание происхождения наборов, полей заявок и инженеров, единиц
измерения и допущений приведено в разделе [«Тестовые данные»](docs/data.md).

Актуальные файлы в корне проекта:

- исходные синтетические и контрольные (`_old`) CSV по каждому району;
- исправленные контрольные данные без противоречий;
- список инженеров с навыками `engineers.csv`;

На основе них автоматически с помощью утилиты могут быть построены JSON,
которые по умолчанию доступны через фронтенд:

- `Югоцентр.json`;
- `Восток.json`;
- `Юго-восток.json`.

JSON генерируется только из синтетических данных в CSV, `engineers.csv` и, если
он есть, указанного контрольного CSV скриптом

```bash
.venv/bin/python -m backend.optimization.scripts.generate_dataset_json
```

Генератор сначала использует постоянный `nominatim_cache.json`. Для новых
адресов он проверяет локальный Nominatim на `http://127.0.0.1:8080/search`,
запрос передаётся через URL-кодирование параметров; если локальный сервис
недоступен, используется публичный Nominatim с интервалом 1,1 секунды и
обязательным User-Agent. Результаты кэшируются. Неточный адрес получает
заметную резервную координату Кремля и выводится как ошибка, чтобы его можно
было исправить вручную.

Генератор учитывает варианты `с`, `стр.`, `строение`, корпуса и адресные
дроби, а также выбирает результат Nominatim, ближайший к офису района, когда
ответов несколько. Установка координат не заменяет проверку адреса на карте.

## Ограничения и дальнейшая работа

- текущая локальная БД — SQLite; модели можно перевести на PostgreSQL, а для
  нескольких диспетчеров нужна транзакционная БД;
- публичный OSRM может ограничивать частоту запросов, поэтому для демонстрации
  нужно заранее прогреть кэш или использовать свой сервер;
- время передвижение на общественном траснпорте равно удвоенному автомобильному
  времени из-за отсутствия качественных GTFS-расписаний транспорта для Москвы
  с учетом метро и электричек и правильного учета всех автобусных остановок;
- оборудование моделируется как утренний запас роутеров без передачи между
  инженерами и пополнения в течение дня;
- ICO-DE и Timefold решатели проигрывают Google OR-Tools и добавлены только с
  целью выявления наилучшего решателя по качеству и скорости.
