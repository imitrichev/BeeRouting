# BeeRouting

BeeRouting — локальный web-прототип для планирования маршрутов выездных
инженеров по кейсу 13 «Интеллектуальный сервис планирования рабочих маршрутов».
Он распределяет заявки, строит порядок посещения, показывает результат на
карте и помогает диспетчеру понять, почему заявка назначена или осталась без
исполнителя.

Проект ориентирован на официальный сценарий из [13.pdf](13.pdf): 10–15
инженеров, до 100 заявок, временные окна, разные навыки и транспорт,
перепланирование в течение рабочего дня и сравнение с простым жадным
алгоритмом.

## Что уже работает

- загрузка трёх официальных районов и пользовательских JSON;
- отдельное хранение плана каждого района, поэтому переключение района не
  требует повторной оптимизации;
- Baseline — заданный ТЗ жадный алгоритм;
- основной `ORToolsOptimizer` на Google OR-Tools;
- экспериментальный `ICOOptimizer` на ICO-DE/random keys и дополнительный
  `TimefoldOptimizer` для сравнения;
- временные окна и рабочие смены как жёсткие ограничения;
- квалификация и тип транспорта как жёсткие ограничения;
- опциональный учёт количества роутеров у инженера;
- расчёт времени движения и расстояния отдельно для каждого типа транспорта;
- OSRM-матрицы и дорожная геометрия маршрута для MapLibre;
- три события перепланирования: срочная заявка, отмена заявки и
  недоступность инженера;
- ручное переназначение с предварительной проверкой, причинами отказа и
  подтверждением изменения метрик;
- создание заявки через интерфейс с геокодированием адреса и нормативной
  длительностью;
- статусы заявок, фиксация уже начатых работ и сохранение плана в БД;
- двухступенчатые структурированные объяснения решения и необязательная
  генерация текста через LLM.

Решение принимает только Optimization Engine. LLM получает факты проверки и
не участвует в назначении заявки.

## Соответствие ТЗ

| Требование 13.pdf | Реализация |
|---|---|
| Распределить заявки и определить порядок визитов | OR-Tools, Baseline, ICO-DE, Timefold |
| Навык заявки входит в навыки инженера | Hard constraint; используются `LOCAL_WORKS`, `CONNECTION_AND_UPSELL`, `EMERGENCY_WORKS` |
| Работа укладывается в смену | Hard constraint с учётом дороги, ожидания и длительности работы |
| Начало работы попадает в окно | Hard constraint; ранний приезд допускает ожидание |
| Тип транспорта | Один из `CAR`, `WALK`, `BICYCLE`, `PUBLIC_TRANSPORT`; матрицы выбираются по инженеру |
| Оборудование | Дополнительный hard constraint; для роутеров учитывается количество, режим можно выключить |
| Обязательные метрики | Число задействованных инженеров и пробег по каждому инженеру и суммарно |
| Показать маршрут на карте | MapLibre, OSRM geometry; старт маршрута — стартовая точка инженера |
| Неназначенные заявки | `unassigned_task_ids` и структурированная причина по каждой заявке |
| Перепланирование | События аварии, отмены и недоступности инженера |
| Объяснение решения | Детерминированные проверки, counterfactual-проверка и необязательный LLM-текст |

Возврат на стартовую точку после последней заявки не требуется, как указано в
ТЗ. Промышленная FSM, авторизация, мобильное приложение, Kafka и
отказоустойчивый production-контур в прототип не входят.

## Модель предметной области

Математическое ядро находится в `backend/optimization` и не импортирует
Django, ORM, frontend или LLM. Основные модели — dataclass:

- `Engineer` — ID, имя, 1–3 навыка, один тип транспорта, стартовая точка и
  доступный запас роутеров;
- `EngineerAvailability` — смена в формате `HH:MM`;
- `Task` — адрес/координаты, один требуемый навык, временное окно,
  `duration_minutes`, тип работ, приоритет, статус и требования к транспорту и
  оборудованию;
- `OptimizationProblem` — инженеры, смены, заявки и routing data;
- `RouteStop` и `EngineerRoute` — расписание и метрики маршрута;
- `OptimizationResult` — маршруты, неназначенные заявки, причины и разложение
  objective.

Единицы проекта:

- границы времени — `HH:MM`;
- длительность работ и travel time — минуты;
- расстояние — километры;
- координаты — `latitude`/`longitude` в WGS84.

Нормативы работ задаются в `backend/optimization/work_norms.py`:

| Тип работ | Полный норматив | Работа после прибытия |
|---|---:|---:|
| Подключение клиентов | 90 мин | 70 мин |
| Авария на ТКД | 100 мин | 80 мин |
| Дозаказ оборудования | 40 мин | 20 мин |
| Локальная заявка/ремонт | 50 мин | 30 мин |

Из полного норматива генератор вычитает 20 минут резервной дороги и записывает
в JSON только работу после прибытия. Фактическая дорога между точками берётся
из routing provider и может отличаться от этих 20 минут.

## Архитектура

```text
CSV / JSON / Nominatim
          |
          v
  JsonScenario + RoutingProvider
          |
          v
  OptimizationProblem (domain)
          |
  +-------+---------+----------------+
  |       |         |                |
  v       v         v                v
Baseline OR-Tools  ICO-DE        Timefold
  +-------+---------+----------------+
          |
          v
  OptimizationResult + explanations
          |
  Django/DRF API v2 -> SQLite/PostgreSQL-compatible ORM -> Vue/MapLibre
```

`RoutingProvider` отделяет источник матриц от solver. Детерминированный
`CoordinateRoutingProvider` нужен для тестов и воспроизводимых сравнений.
`OSRMRoutingProvider` получает дорожные матрицы и GeoJSON-линии маршрутов.
Solver получает матрицы извне и не строит их самостоятельно.

Для каждого инженера используется матрица его `vehicle_type`. Если provider
передал профильные матрицы, время и расстояние для автомобиля, пешего режима,
велосипеда и общественного транспорта различаются. Стандартный OSRM не
рассчитывает расписание общественного транспорта, поэтому `PUBLIC_TRANSPORT`
использует автомобильный граф и удвоенное время как явно зафиксированное
приближение. Пеший и велосипедный режимы требуют соответствующих OSRM
endpoint'ов или собственного многопрофильного сервера.

Подробное устройство математической модели описано в
[docs/solver.md](docs/solver.md).

## Данные и геокодирование

Актуальные официальные файлы в корне проекта:

- `Югоцентр.json`;
- `Восток.json`;
- `Юго-восток.json`;
- `engineers.csv`;
- исходные синтетические и контрольные CSV по каждому району.

JSON генерируется только из синтетического CSV, `engineers.csv` и, если он
есть, контрольного CSV. Готовый JSON не является источником генерации.

```bash
.venv/bin/python -m backend.optimization.scripts.generate_dataset_json
```

Генератор сначала использует постоянный `nominatim_cache.json`. Для новых
адресов он проверяет локальный Nominatim на `http://127.0.0.1:8080/search`,
запрос передаётся через URL-кодирование параметров; если локальный сервис
недоступен, используется публичный Nominatim с интервалом 1,1 секунды и
обязательным User-Agent. Результаты кэшируются. Неточный адрес получает
заметную резервную координату Кремля и выводится как ошибка, чтобы его можно
было исправить вручную.

Генератор учитывает варианты `с`, `стр.`, `строение`, корпуса и адресные
дроби, а также выбирает результат Nominatim, ближайший к офису района, когда
ответов несколько. Установка координат не заменяет проверку адреса на карте.

## Быстрый запуск

Команды выполняются из корня проекта.

### Основное окружение

Основное приложение сейчас запускается в `.venv`. В моей текущей рабочей
копии это Python 3.14. Основной проект, Django и OR-Tools устанавливаются в
это окружение; Timefold туда устанавливать не нужно.

Проверить версию Python перед созданием окружения:

```bash
python3 --version
```

Создать и заполнить основное окружение:

```bash
python3 -m venv .venv
.venv/bin/python --version
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python backend/web_mvp/manage.py migrate
```

Корневой `requirements.txt` — агрегатор: он подключает
`backend/optimization/requirements.txt` и `backend/web_mvp/requirements.txt`.
`requirements-dev.txt` дополнительно подключает dev-зависимости ядра, включая
pytest. Timefold намеренно вынесен в отдельный
`backend/optimization/requirements-timefold.txt`, потому что требует отдельную
совместимую версию Python и JVM.

### Отдельное окружение Timefold

Timefold Python API в текущей конфигурации требует Python 3.10–3.12. Поэтому
Timefold устанавливается рядом, в `.timefold-venv`, а не в `.venv`. У коллеги
не будет каталога `.tools`: это локальная, игнорируемая Git папка этой машины.

Сначала проверьте наличие Python 3.12:

```bash
python3.12 --version
```

Если команда есть, создайте окружение:

```bash
python3.12 -m venv .timefold-venv
.timefold-venv/bin/python -m pip install \
  -r backend/optimization/requirements-timefold.txt
```

Если Python 3.12 отсутствует в Ubuntu, его можно установить так:

```bash
sudo apt update
sudo apt install python3.12 python3.12-venv
```

Затем повторите создание `.timefold-venv`. Не создавайте Timefold-окружение
командой `python3 -m venv`, если `python3 --version` показывает 3.14.

Timefold также требует JDK 17 или новее. Проверьте его:

```bash
java -version
```

Если Java установлена и находится в `PATH`, запустите полный benchmark так:

```bash
PYTHONPATH="$PWD" \
.timefold-venv/bin/python \
  -m backend.optimization.benchmarks.benchmark_yugo_center \
  --include-timefold \
  --routing-provider coordinate \
  --iterations 1 \
  --timefold-time-limit-seconds 20
```

Если Java установлена в нестандартный каталог, задайте `JAVA_HOME`:

```bash
JAVA_HOME=/path/to/jdk-21 \
PATH="$JAVA_HOME/bin:$PATH" \
PYTHONPATH="$PWD" \
.timefold-venv/bin/python \
  -m backend.optimization.benchmarks.benchmark_yugo_center \
  --include-timefold --routing-provider coordinate --iterations 1
```

Схема окружений такая:

| Что запускается | Python | Окружение |
|---|---|---|
| Django, API, frontend-сценарий, OR-Tools, Baseline | системный Python проекта, сейчас 3.14 | `.venv` |
| Benchmark с Timefold | Python 3.10–3.12 + JDK 17+ | `.timefold-venv` |

Веб-интерфейс сейчас запускает Baseline и OR-Tools. Timefold подключён как
отдельный solver для сравнительного benchmark и не требуется для запуска
Django.

### Backend

```bash
.venv/bin/python backend/web_mvp/manage.py runserver 8000
```

### Frontend

Во втором терминале:

```bash
cd frontend
npm install
npm run dev
```

Откройте <http://127.0.0.1:5173>.

### Локальные Nominatim и OpenTripPlanner

Если нужен локальный геокодер и routing-сервис, установите Docker и выполните
из корня:

```bash
bash install.sh
```

Скрипт скачивает OSM/GTFS при отсутствии файлов, собирает граф OTP и запускает
`routing/docker-compose.yml`: Nominatim доступен на `8080`, OpenTripPlanner —
на `8081`. Сборка графа и загрузка карты занимают заметное время и требуют
несколько гигабайт памяти. После запуска генератор JSON использует локальный
Nominatim автоматически; OSRM для дорожных матриц настраивается отдельно через
`OSRM_BASE_URL` или транспортные `OSRM_*_BASE_URL`.

Для разработки JSON-проверки в окне объяснения доступны по умолчанию. Для
режима без технического JSON можно запустить backend так:

```bash
BEEROUTING_MODE=production .venv/bin/python backend/web_mvp/manage.py runserver 8000
```

### Сценарий демонстрации

1. Нажмите «Перезагрузить официальный датасет». Это очищает сохранённое
   состояние и заново загружает три района.
2. Выберите район в списке. Каждый район хранит собственный результат.
3. Нажмите `Baseline (жадный алгоритм)`, чтобы показать простой вариант, или
   `Распределить заявки (OR-Tools)` для основного расчёта.
4. Выберите инженера или флажок на карте. Серые точки становятся цветными,
   показываются номера порядка обхода, офис отмечен домиком.
5. Откройте облачко у заявки. В developer-режиме видны структурированные
   проверки, в production-режиме — только понятный текст.
6. Покажите «Сценарии перепланирования...» и выберите аварийную заявку,
   отмену заявки или недоступность инженера.
7. Для ручного переназначения сначала выполните preview: интерфейс покажет
   причины невозможности или старые и новые метрики, затем отдельное
   подтверждение изменит план.

Кнопка «Статусы заявок из контрольного распределения» нужна только для
демонстрации быстрого восстановления статусов. Она переносит статусы из
контрольного CSV, но сохраняет текущих инженеров рабочего плана и не запускает
OR-Tools. Само контрольное распределение составителей используется для
сравнения в benchmark и может нарушать hard constraints.

## API v2

API доступен под `/api/v2/`; старого API v1 в проекте нет. Подробный контракт
описан в [docs/api-v2.md](docs/api-v2.md).

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/api/v2/territories/` | Список загруженных районов |
| `GET` | `/api/v2/dataset/?territory=...` | Текущий dataset и сохранённый план |
| `GET` | `/api/v2/dataset/official/` | Перезагрузка трёх официальных районов |
| `POST` | `/api/v2/dataset/upload/` | Загрузка JSON в поле `file` |
| `POST` | `/api/v2/optimize/` | Baseline или OR-Tools |
| `POST` | `/api/v2/sync-reference-statuses/` | Синхронизация статусов контрольного CSV |
| `POST` | `/api/v2/tasks/` | Создание заявки с нормативной длительностью |
| `POST` | `/api/v2/geocode/` | Проверка адреса и координат |
| `POST` | `/api/v2/replan/` | Три события перепланирования |
| `POST` | `/api/v2/manual-reassignment/preview/` | Проверка ручного переноса |
| `POST` | `/api/v2/manual-reassignment/confirm/` | Подтверждение переноса |
| `POST` | `/api/v2/explain/<task_id>/` | Объяснение результата |

Детальные CRUD-маршруты инженеров, заявок, справочников и событий также
зарегистрированы через API v2. Сложная логика находится в сервисах, а не во
views и serializers; математическое ядро от Django не зависит.

## Benchmark и решатели

Основной сравнительный сценарий —
`backend/optimization/benchmarks/benchmark_yugo_center.py`. Он сравнивает
контрольный план составителей, Baseline и OR-Tools; ICO-DE и Timefold
подключаются отдельно. Benchmark выводит время, назначенные заявки,
неназначенные заявки, задействованных инженеров, расстояние, travel time,
декомпозицию objective, процентное сравнение OR-Tools с Baseline и пробег по
каждому инженеру.

```bash
.venv/bin/python -m backend.optimization.benchmarks.benchmark_yugo_center \
  --routing-provider coordinate --iterations 1
```

Для реальных дорог:

```bash
.venv/bin/python -m backend.optimization.benchmarks.benchmark_yugo_center \
  --routing-provider osrm --iterations 1 --osrm-timeout-seconds 30
```

Все четыре варианта:

```bash
.venv/bin/python -m backend.optimization.benchmarks.benchmark_yugo_center \
  --include-ico-de --include-timefold \
  --routing-provider osrm --iterations 1
```

`--ignore-task-statuses` строит полный новый утренний план по всем заявкам.
Без него `CANCELLED` и `COMPLETED` исключаются, `EN_ROUTE` и `IN_PROGRESS`
фиксируются, а `ASSIGNED` можно переносить. `--preserve-assigned` дополнительно
фиксирует и `ASSIGNED`. `--consider-equipment` включает количественный учёт
роутеров. OSRM использует SQLite-кэш пар и NPZ-кэш матриц; coordinate provider
кэш не использует.

Подробные команды, параметры и интерпретация результатов собраны в
[docs/benchmarks.md](docs/benchmarks.md).

Кратко о решателях:

- **Baseline** — заявки идут по входному порядку, инженеры проверяются по
  входному порядку, глобального поиска нет. Это эталон из ТЗ.
- **OR-Tools** — основной solver VRPTW: одновременно выбирает инженера,
  порядок, расписание и допустимые пропуски; оптимизирует число инженеров,
  пробег и travel time с настроенными штрафами.
- **ICO-DE** — экспериментальная метаэвристика с random keys. Используется
  для сравнения и исследований, но не заменяет OR-Tools.
- **Timefold** — дополнительный solver с planning list variable и constraint
  streams. Нужны отдельное Python-окружение и JDK 17+; отсутствие Java не
  мешает запуску Baseline и OR-Tools.

Подробное объяснение OR-Tools, ограничений, матриц и результата — в
[docs/solver.md](docs/solver.md).

## Ограничения и дальнейшая работа

- текущая локальная БД — SQLite; модели можно перевести на PostgreSQL, а для
  нескольких диспетчеров нужна транзакционная БД;
- публичный OSRM может ограничивать частоту запросов, поэтому для демонстрации
  нужно заранее прогреть кэш или использовать свой сервер;
- `PUBLIC_TRANSPORT` — оценочное удвоение автомобильного времени, а не
  расписание общественного транспорта;
- equipment моделируется как утренний запас роутеров без передачи между
  инженерами и пополнения в течение дня;
- долгие расчёты пока синхронны;
- ICO-DE и Timefold остаются сравнительными экспериментами;
- LLM не является источником решения и не должна добавлять причины, которых
  нет в структурированном результате проверки.

Полный официальный документ остаётся в [13.pdf](13.pdf), а актуальные
детали реализации вынесены в [docs/](docs/).
